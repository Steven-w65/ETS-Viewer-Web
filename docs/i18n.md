# Internationalization

ETS Viewer uses i18next 26, react-i18next 17 and i18next-browser-languagedetector 8.
All translation resources are bundled with the static frontend. There is no remote
translation backend, runtime resource download, or translation of imported content.

## Registry and rendering

`src/i18n/locales.ts` is the single supported-locale registry. Every entry has a
canonical code, native name, resource object, optional matching aliases and optional
text direction. English (`en`, English) and Simplified Chinese (`zh-CN`, 简体中文)
are ordinary entries; there are no English/Chinese branches in detection or JSX.

The initial packs are split into base, app, reading and importing JSON fragments
for maintainability and merged when registered. Keys are flat dotted names such
as `settings.language` and `reader.referenceAnswer`, with `keySeparator: false`.
One i18next translation namespace supports functional groups, interpolation and
locale cardinal plural forms. React escapes text; imported HTML never enters a
translation string or an HTML injection API.

`src/i18n/index.ts` initializes bundled resources synchronously, connects React,
and updates the resolved `html.lang` and `html.dir`. Components use
`useTranslation()`. Translation changes rerender existing components without
replacing the application, Reader, disclosures, dialogs or media elements.

`questionTypeLabels.ts` maps the eight collector types to `questionTypes.*` keys,
with a neutral unknown key. The same keys localize navigation and Answer Preview.
The selector returns a key instead of a hardcoded display name; normalized types,
source values, numbering and stable IDs do not change.

## Auto and manual preference

Settings → Language lists Auto followed by every registry entry's native name.
Adding a locale requires no selector JSX or preference-manager changes.

`languagePreference.ts` stores only `auto` or an exact registered locale code in
`ets-language`. Auto remains Auto when its resolved language changes. Invalid or
removed saved locales resolve as Auto. Blocked storage leaves switching available
in memory. Appearance continues using its separate `ets-appearance` preference.
No imported JSON, answers, media, warnings or Blob URLs are persisted.

The detector is restricted to `navigator`, with `caches: []`. Legacy detector
storage such as `i18nextLng`, URL parameters, cookies and the previous document
language cannot override the application preference. The detector's public API
provides the ordered browser preferences; `changeLanguage()` applies the result.
Auto also responds to the browser's `languagechange` event during the session.

`languageMatching.ts` negotiates each browser preference in order:

1. Canonicalize the identifier using `Intl.getCanonicalLocales`.
2. Prefer an exact registered code across the entire registry.
3. Consider explicit registered aliases.
4. Consider the same language with a compatible `Intl.Locale.maximize()` script,
   preferring a matching region and then a neutral language resource. Registry
   order breaks remaining equal matches deterministically.
5. Continue with the next browser preference if none match. After exhausting
   preferences, use the configured fallback (`en` initially).

Invalid identifiers are skipped. For example, `zh-SG` can use a compatible Hans
resource, while `zh-TW`/`zh-Hant` do not silently select a Hans pack. Registering a
Hant resource makes it eligible without changing the matcher. The same rule applies
to any language with multiple writing systems. Explicit aliases should be rare and
documented; they cannot override an exact newly registered regional resource.

## Adding a locale

1. Create a complete resource file, for example `src/i18n/resources/fr.json`.
   Use the same flat keys as the combined English pack (the four `*.en.json`/`en.json`
   files). A new pack can use one file or functional fragments.
2. Translate UI values and retain interpolation names such as `{{count}}`,
   `{{filename}}` and `{{paper}}`. Supply the locale's cardinal forms, as reported
   by `Intl.PluralRules(code).resolvedOptions().pluralCategories`; some languages
   need more forms than English. Do not replace ordinary keys with `_other` keys.
3. Import the resource and add one registry entry:

   ```ts
   import fr from './resources/fr.json';
   // In supportedLocales:
   { code: 'fr', nativeName: 'Français', resources: fr }
   ```

   Add `dir: 'rtl'` when needed; otherwise direction follows i18next's locale
   metadata. Add only genuinely necessary aliases.

4. Run `npm run test:i18n`, `npm test` and `npm run build`. Add cases for the new
   locale's matching, plural forms and representative translated UI.

The entry automatically populates Settings and participates in Auto negotiation.
Do not modify Settings JSX, language-switching code, component hooks or the matcher.

`validateResources()` discovers packs through the registry and checks string
values, missing/unexpected functional keys, ordinary versus plural-key parity,
required locale plural forms, and interpolation parameters in each variant.
Future packs receive the same checks as the first two. i18next still falls back to
English for a missing runtime key; validation catches incomplete registered packs
before release. Native locale names and source-language data need no translation.

## Coverage and data boundaries

Localized areas include welcome/import/progress/errors; the exact-path folder
guide and clipboard statuses; header, Settings and themes; navigation, dates,
statistics and empty states; Reader cards and source notes; Answer Preview;
warnings and technical-detail labels; media fallbacks and accessible names;
export controls and existing notifications; and formatting-limit notices.

Warnings translate structured category/code/parameters over the existing Issue
state. Filenames, source JSON paths and attempted/resolved paths stay verbatim.
Optional message keys/parameters support future diagnostic producers. Unknown
codes use a truthful localized generic description; original internal diagnostic
text remains available locally in memory. Worker errors carry a translation-free
descriptor; the worker does not load i18next or translation packs.

The following remain unchanged: imported paper names, prompts, options, passages,
answers, transcript text, source files, media references, official numbers,
per-group preview display numbers, accepted-answer precedence, and export bytes.
Only known parser-authored supplement labels are translated; unknown source
labels remain intact. The two folder-guide paths are copied exactly:

```text
%APPDATA%\ETS
/storage/emulated/0/Android/data/com.ets100.secondary/files/Download/ETS_SECONDARY/resource
```

The bounded HTML formatter accepts a pure reference-label formatter so only its
generated labels translate, never matching literal text from a question. It also
retains audio/video reference text encountered after the formatting limit.

## Verification

Final results: 272 tests in 35 files; 42 i18n tests in six files; TypeScript and
production build passed. Edge passed 53 dedicated i18n checks, 49 existing UI checks,
69 preview checks and 32 native-media checks. Windows WebKit passed 51 dedicated
i18n checks, 49 UI checks, 66 preview checks and 19 media-fallback checks. Reference
parity matched 1,744 stored answers and five legacy exports; 188 checked desktop
files remained unchanged. The packs contain 213 English and 208 Chinese keys (the
count difference is required plural forms), with no fragment-key collisions.

The six `tests/i18n*` suites cover generic matching, scripts, alias priority,
persistence, blocked storage, resource validation, a third registered French test
locale, all localized component groups, counts, original source data and paths,
open dialog/Settings state, focus, expanded cards, scroll and media identity.
Review regressions reproduce exact-code/alias priority and ordinary/plural-key
validation failures before the fixes.

`tools/browser-i18n.mjs` uses synthetic local ZIP content and verifies Auto/manual
preferences, stale-cache isolation, actual native clipboard copy in Edge,
unchanged import counts, playing audio continuity, source text and local preview
numbers, identical English/Chinese export bytes, open dialogs, reload/privacy,
blocked storage and 320/390px layouts. Screenshots are ignored under `.qa/i18n-browser/`.
The script starts its own local preview on port 4192 and stops it afterwards.

Actual results and remaining browser limitations are recorded in
[verification.md](verification.md). Playwright WebKit on Windows is not a real
Safari/device test. Native player controls are localized by the browser itself.
No deployment is performed as part of these checks.
